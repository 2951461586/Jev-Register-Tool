## 1. 🔴 P0：台账"升级语义"完全失效，且会静默清空已捕获的 `api_key`

### 现象

`ledger.py` 的等级表与 `pipeline.py` 实际写入的状态**根本不是同一套词汇**：

```python
# src/ledger.py:20
RANK = {"success": 2, "partial": 1, "skipped": 0, "failed": 0, "": 0}
```

```python
# src/pipeline.py 实际写入的 status
applied / confirmed / approved / registered / keyed / failed / partial / code_sent
```

实测评分：

```
rank('applied')    = 0        rank('keyed')    = 0
rank('confirmed')  = 0        rank('failed')   = 0
rank('approved')   = 0        rank('partial')  = 1
rank('registered') = 0        rank('code_sent')= 0
```

`success` / `skipped` 是**兄弟项目（批量注册类）的口径**，本项目一个都没写过。
于是 `keyed` 和 `failed` 同分。

### 后果（已复现）

`merge()` 在同级时走"并集、新值胜出"：

```python
# ① 成功记录
{"status": "keyed", "api_key": "apikey_LIVE_ABC", "error": ""}
# ② 同 key 再来一条 failed（重跑、超时重试、任何失败路径）
{"status": "failed", "api_key": "", "error": "认证回调 HTTP 401: Code expired"}
```

`api_key` 被**覆盖成空串**。原因：`AccountRecord.to_dict()` 无条件输出 `api_key` 键
（失败时值为 `""`），并集合并时新值胜出。

同理 `partial`（rank=1）> `keyed`（rank=0）⇒ 走 `return dict(new)` **整体替换**，
旧记录字段全丢。

### 影响面

`tools/verify_keys.py` 从台账读 `api_key`：

```python
recs = [r for r in led.load() if r.get("api_key")]
```

被降级的账号会**从验收清单里静默消失** —— 不是报错，是少几行。而验收报告的
"可用 15 / 不可用 0"恰恰是项目的核心交付指标。

### 为什么现在还没出事（是运气，不是设计）

真实台账 23 行 / 15 个 key，其中 5 个 key 有重复行。逐条核对行序：

```
oai-ecc230d8aa7f4bf2@example-mail.test
    line  3  status=failed     api_key=无
    line  4  status=failed     api_key=无
    line  5  status=failed     api_key=无
    line  6  status=keyed      api_key=有
    line 10  status=keyed      api_key=有
    -> 末行 status=keyed | 存在 failed 排在 keyed 之后: False
```

**5 个 key 的 `failed` 行全部排在 `keyed` 行之前。** 因为所有状态同分，
`load()` 退化成"最后一行胜出"，所以侥幸无损。

只要**任何一次**重跑在成功之后失败（`--mode resume` 重试、`claim` 二次提交、
`watch` 重复消费），数据就会被静默破坏。

### 为什么自测没拦住

`selftest.py::test_ledger_union` 用的词汇是 `success` / `failed`：

```python
led.append({"key": "a@x.com", "status": "success", "api_key": "k1"})
...
led.upsert_many([{"key": "a@x.com", "status": "failed", "error": "x"}])
check("[负对照] 低等级不会覆盖高等级", rec.get("status") == "success")
```

`success` 正好是 `RANK` 认的那套 ⇒ **断言必过**。
**负对照存在，但对照的是错的词汇。** 这比没有负对照更危险：它给出虚假的安全感。

### 建议修法（两条路，各有取舍）

**A. 修 `RANK`，对齐真实词汇**（作用域最小）

```python
RANK = {"keyed": 5, "registered": 4, "approved": 3, "confirmed": 2,
        "applied": 1, "code_sent": 1, "partial": 1, "failed": 0, "": 0}
```

- 效果：`keyed` 后写 `failed` ⇒ `r_new < r_old` ⇒ 保留旧记录，`api_key` 不丢
- 取舍：**失败信息也被丢掉了**。想要"保住 key 又记下这次失败"，需要
  `merge` 在"保留旧记录"时把 `new.error` 并进 `last_error` 字段

**B. 让失败态不碰身份字段**（更本质，但要改 `merge`）

在 `merge()` 里区分"状态等级"与"字段所有权"：失败态只允许写
`error` / `stages` / `timings`，不允许清空 `api_key` / `api_key_id` / `user` / `waitlist`。

> 无论选哪条，**必须同时补一条用真实词汇的负对照**：
> `keyed` 之后写 `failed`，断言 `api_key` 仍在。否则同类问题会再犯一次。

## 3. P1：客户端取码仍是宽松正则，服务端已加固 —— 同一个坑的孪生版本

服务端（Worker D1 规则）因为"邮件头里的 `MTA74-AB1` 压过正文真码"，
已把 OTP 抽取改成锚定式：

```
(?<![A-Za-z0-9])(\d{6})(?=\s+is\s+your\s+one-time\s+code)
```

客户端 `pipeline.py:199` 还是老写法：

```python
codes = re.findall(r"\b\d{6}\b", m.body)
...
res = cl.auth_callback(codes[0], "otp", rec.email)
```

**取第一个 6 位数字**。若 `m.body` 里出现任何先于真码的 6 位串
（引用头、跟踪 ID、时间戳片段），就会提交错码，表现为
`401 Code expired` —— 而这个错误码在 runbook 里的处置是"重新发码"，
**会把 bug 引向错误的方向**。

**建议**：把服务端已确立的锚定 pattern 同步到客户端，做**双路**：
锚定式优先，命中失败才退回宽松式并**在日志里标明走了降级路径**。

## 4. P1：`run_e2e.py` 的 `claim` 分支被切成两段

```python
if args.mode == "claim":          # line 151
    ...
    if recs[0].status == "code_sent":
        return 0                  # 提前返回
    # ← 否则穿透到下面

if args.mode == "watch":          # line 168
    ...

if args.mode == "resume":         # line 176
    recs = pipe.resume(...)
elif args.mode == "claim":
    pass  # recs 已在上面的 claim 分支里算好   ← line 182
else:
    recs = pipe.run_batch(...)
```

当前**逻辑是对的**，但这个形态正是本项目记忆里踩过的坑（"往一串 `if` 分支里插新分支前，
先确认末尾是不是 `if/else` 收尾；否则新分支会穿透进 `else`"）。

风险：`claim` 的"算 recs"与"用 recs"隔着 30 行和两个 `return` 点。
任何人加一个模式、或改动上面某个 `return` 条件，`recs` 就可能未定义或串到
`run_batch` 上去。

**建议**：把 claim 收成一个函数 `cmd_claim(args) -> tuple[int, list]`，
主流程只做分派，不共享局部变量。

## 7. P2：无并发（架构债已自认，但没落地设计）

15 个账号串行约 2.5 分钟，瓶颈在"发码 → 收码"的邮件往返（3~6s）。
`architecture.md` §6 已把它列为债，但没有落地路径。

可并行的边界其实很干净：

| 阶段 | 能否并行 | 理由 |
|---|---|---|
| `stage_apply` | ✅ 完全独立 | 每个账号建自己的邮箱、自己提交、自己等确认 |
| `stage_wait_approval` | ✅ | 只是查索引端点 |
| `stage_login` | ✅ | 邮件往返独立，`since_ms` 已按账号隔离 |
| `stage_create_key` | ✅ | 各自会话 |
| `watch` | ❌ **必须串行** | 读的是**全表共享窗口**（100 行），并发读只会互相挤 |

**注意**：`Pipeline.client` 是**实例级共享字段**（`self.client`），
`stage_login` 写它、`stage_create_key` 读它。串行时没暴露，
**一旦上并发就会串号**（A 账号的 key 建在 B 账号的会话上）。
上并发前必须先把 `client` 改成**返回值传递**或每账号一个 `Pipeline` 实例。

> 这条比"加线程池"重要得多 —— 先改数据流，再谈并发。

## 10. P3：文档漂移（4 处，已实测）

| 文档 | 写的 | 实测 |
|---|---|---|
| `architecture.md` §3 依赖表 | `config` 被依赖 **4** | **8** |
| 同上 | `typesafe` 3 / `framer_waitlist` 2 / `mailrules` 2 | **4 / 3 / 3** |
| `architecture.md` §2 模块表 | `_bootstrap.py` **33** 行 | **37** 行 |
| `mail-filters.md` 开头 | mailrules 段 **19** 项 | **18** 项（总数 37 正确） |

### 根因：文档附录那段"AST 复算脚本"本身有 bug

```python
elif (n.module or '').startswith('src.'):
    cnt[n.module.split('.')[1]] += 1
```

`from src import config` 的 `n.module` 恰好是 `"src"`（**不带点**），
不满足 `startswith('src.')` ⇒ **所有 `tools/*` 的顶层 `from src import X` 全被漏计**。

复算对比：

```
文档脚本产出: [('config',4), ('ledger',4), ('tempemail',4), ('typesafe',3),
              ('framer_waitlist',2), ('mailrules',2), ('pipeline',1)]
修正后产出:   [('config',8), ('ledger',4), ('tempemail',4), ('typesafe',4),
              ('framer_waitlist',3), ('mailrules',3), ('pipeline',1)]
```

**这不是数字笔误，是工具错了。** 而文档特意声明"依赖关系是用 AST 算出来的，
不是凭印象画的" —— 恰恰是这个"可复算"的承诺给出了错误的安全感。

修正只需加一个分支：

```python
elif n.module == 'src':
    for a in n.names:
        cnt[a.name] += 1
```

import ast
from pathlib import Path
from collections import Counter
cnt = Counter()
for p in sorted(list(Path('src').glob('*.py')) + list(Path('tools').glob('*.py'))
                + list(Path('tools/probes').glob('*.py'))):
    for n in ast.walk(ast.parse(p.read_text(encoding='utf-8'))):
        if isinstance(n, ast.ImportFrom):
            if n.level and n.module:      cnt[n.module] += 1
            elif n.level:
                for a in n.names:         cnt[a.name] += 1
            elif n.module == 'src':
                for a in n.names:         cnt[a.name] += 1
            elif (n.module or '').startswith('src.'):
                cnt[n.module.split('.')[1]] += 1
print(cnt.most_common())
